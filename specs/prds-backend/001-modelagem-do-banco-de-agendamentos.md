## Problem Statement

O backend precisa de um esquema de banco consistente para representar o paciente de demonstração, especialidades, profissionais e consultas, garantindo integridade referencial e impedindo conflitos de agenda.

## Solution

Criar migrations e seeders PostgreSQL para um modelo baseado em UUIDs, com consultas contendo início e fim, status controlado, relacionamentos obrigatórios e restrições de não sobreposição para profissionais e pacientes.

## User Stories

1. As the scheduling system, I want to store a demonstration patient, so that appointments have a valid patient reference without requiring registration or authentication.
2. As the scheduling system, I want to store specialties, so that professionals can be organized by medical area.
3. As the scheduling system, I want each professional to belong to one specialty, so that the professional-specialty relationship is consistent.
4. As the scheduling system, I want to store appointments with patient, professional, time range, status, and optional observations, so that the consultation history is complete.
5. As the scheduling system, I want UUID identifiers, so that records have stable non-sequential identifiers.
6. As the scheduling system, I want to prevent overlapping active appointments for a professional, so that a professional cannot be booked twice at the same time.
7. As the scheduling system, I want to prevent overlapping active appointments for a patient, so that a patient cannot have two consultations at the same time.
8. As the scheduling system, I want canceled appointments to release their time range, so that the professional and patient can be scheduled again.
9. As the scheduling system, I want appointment statuses constrained to the supported values, so that invalid states cannot be persisted.
10. As a developer, I want the seeder to be idempotent, so that repeated execution does not duplicate reference or demonstration data.

## Implementation Decisions

- Use PostgreSQL as the database.
- Use plural Laravel table names: `patients`, `specialties`, `professionals`, and `appointments`.
- Use UUID primary keys generated by the application. The demonstration patient uses a fixed UUID documented for the mobile application.
- Keep `patients` to the PDF minimum: identifier and name. Do not add age.
- Store specialty and professional names as required strings. Specialty names are unique case-insensitively; professional names are not unique.
- Store `professional_id` and `specialty_id` as required foreign keys. A professional belongs to exactly one specialty.
- Store required `patient_id` and `professional_id` foreign keys on appointments.
- Use `scheduled_at` and `ends_at` as required timestamps with time zone. Appointment duration is 45 minutes and is calculated by application code, not enforced as an exact duration by the database.
- Enforce `ends_at > scheduled_at` in the database.
- Store optional observations as nullable unrestricted text.
- Store status as a required string with default `scheduled` and a database check constraint allowing only `scheduled`, `confirmed`, `completed`, and `canceled`.
- Use PostgreSQL `btree_gist` and exclusion constraints over half-open time ranges `[scheduled_at, ends_at)` to reject overlaps for the same active professional and for the same active patient. The constraints exclude rows with status `canceled`.
- Add indexes for foreign keys and the range-conflict constraints.
- Use `ON DELETE RESTRICT` for all foreign keys. Do not use soft deletes.
- Include Laravel `created_at` and `updated_at` timestamps.
- Seed 3 specialties, 6 professionals distributed as 2 per specialty, 1 demonstration patient, and at least 2 appointments for each status. Use relative dates: scheduled and confirmed in the future, completed in the past, and deterministic UUIDs for idempotent reseeding.
- Do not create availability, status, or appointment-duration tables.

## Testing Decisions

- Test externally observable database behavior through migration and seeder integration tests.
- Verify all required tables, columns, UUID primary keys, foreign keys, nullability, defaults, timestamps, and indexes.
- Verify specialty case-insensitive uniqueness and allowed appointment statuses.
- Verify invalid appointment ranges are rejected.
- Verify overlapping active appointments are rejected for both the same professional and the same patient.
- Verify adjacent ranges are allowed and canceled appointments do not block reuse.
- Verify foreign-key deletion is restricted and repeated seeding does not duplicate records.
- No comparable domain tests currently exist; use the database integration seam rather than unit-testing migration implementation details.

## Out of Scope

- Patient registration, user registration, and authentication.
- API routes, controllers, services, and request validation.
- Appointment confirmation or completion workflows.
- Professional working hours, availability, holidays, and blocked periods.
- Appointment types, variable durations, and scheduling history/audit tables.
- Deletion endpoints and soft-delete behavior.

## Further Notes

- The fixed demonstration patient UUID and its configuration must be documented in the project README.
- The patient-overlap rule and fixed 45-minute duration are intentional additions/clarifications beyond the minimum PDF requirements.
- New appointments must not be created in the past; this temporal rule belongs to application validation, not a static database check constraint.
